# EarlyHer frontend

A touch-first breast-health tool for kiosks in Nigerian primary healthcare centres and community outreaches. It also works in desktop, tablet and phone browsers. EarlyHer has a separate landing page, so this application opens straight into the tool. The Python backend and AI services are built separately and are not part of this repository.

EarlyHer helps people understand their symptoms and reach professional care. It does **not** diagnose, score risk, prescribe or recommend treatment. People use it anonymously; nothing needs an account.

> **The triage is a working specification, not a clinically validated algorithm.** The breast-concern and self-check questions, branching and urgency rules implement the supplied working specification. Every unresolved clinical decision is isolated and listed in [docs/clinical-review.md](docs/clinical-review.md), which must be reviewed before live use. Yoruba text is an AI-assisted draft awaiting review by a fluent Yoruba speaker and the clinical lead (see [docs/yoruba-review.md](docs/yoruba-review.md)).

## Run and build

Requires Node 22.5 or later (Node's built-in SQLite is used by the facility import script). Developed on Node 25.

```bash
npm install
npm run dev          # http://localhost:3000, demo-state panel and interface-test questionnaire on
npm run build        # production build
npm start            # serve the production build (needed to test offline)

npm test             # unit tests (Vitest)
npm run lint         # ESLint (eslint-config-next)
npm run typecheck    # TypeScript (run after a build or dev start so route types exist)
npm run verify:browser                 # browser checks against `npm start`
npm run verify:browser -- --fixtures   # also demo-state checks; build with NEXT_PUBLIC_SHOW_DEV_FIXTURES=true
npm run audio:status -- yo   # Yoruba recordings: recorded, outdated, missing; writes audio-scripts/yo.csv
npm run audio:warm -- yo http://localhost:3000   # pre-generate Yoruba speech (needs a provider)
```

If `typecheck` or `build` reports missing modules under `.next/dev/types` for routes that no longer exist, delete `.next/dev/types` (generated by an older `next dev` run) and try again.

| Route | Screen |

## Triage

Both journeys share one flow (`components/triage/triage-flow.tsx`). The model is split so content, navigation, rules and UI can change separately:

- `lib/triage/questions.ts`: stable question ids (Q1, R1–R5, A1–A9, B1–B8, C1–C7, D1–D6, H1–H5, N1–N4), stages and typed option ids.
- `lib/triage/flow.ts`: replays the journey from the stored answers to build the path, the deduplicated branch queue (A, B, C, D, with newly disclosed branches inserted after the current one), skipped questions and the early Red exit. Moving on from a screen removes answers that no longer apply.
- `lib/triage/rules.ts`: deterministic urgency. Rules set a *minimum* level or add a named Yellow *flag*; flags are counted once; combinations (two flags → Orange, history risk plus Yellow → Orange) and exceptions (D4, D5, the injury exception) are applied in one place. Nothing is decided by AI.
- `TRIAGE_POLICY` in `rules.ts` holds the switches for unresolved paths. A single isolated Yellow flag, or a previous scan that needed follow-up on an otherwise routine result, shows a review-safe result ("Talk to a health professional", no timeframe) until the clinical lead decides.

One question per screen, except the short same-screen follow-ups (which breast, headaches or vision, pain disruption, mother's age). Single-choice answers move on after 300 ms (not while moving with arrow keys); multi-select screens use Continue. Back restores earlier answers. "I need help now" opens urgent guidance at any point without changing the result. Progress shows the stages (About you, Safety check, Your symptom, Your history), not a question count.

An early Red result (for example fever with recent redness) shows urgent actions straight away and marks the assessment incomplete; "Answer a few more questions for your doctor" continues from the next question.

**Clinical review:** see [docs/clinical-review.md](docs/clinical-review.md). `npm test` pins every rule, combination and exception.

### Doctor summary

`/summary` lists the applicable answers exactly as chosen (uncertainty and duration ranges kept), the result and reasons, and whether the assessment was cut short. The PDF is built in the browser by `lib/triage/pdf.ts` (no library, works offline) with the standard Helvetica font, which cannot show Yoruba tone marks or ẹ, ọ, ṣ, so the PDF is always in English (the on-screen summary follows the selected language, and says the PDF is English). Embedding a Unicode font would allow a Yoruba PDF. Sharing uses the device share sheet, only when the person presses Share; nothing is uploaded. The filename is neutral (`health-summary.pdf`).

### Reminders and booking

There is no messaging or scheduling service. Reminders (self-check tomorrow, recheck in 2 weeks, monthly self-check) are calendar files (`.ics`) the person adds to their own calendar, and the screen says EarlyHer sends nothing. Booking is an integration point only: `lib/services/booking.ts` defines the interface and the window rules (within 7 days for "this week", 28 days for "within 4 weeks", routine otherwise, never in place of urgent care) and `bookingService` is `null`, so no booking action is shown.

## Languages

The header switches between English and Yorùbá. The choice is a display preference, kept in `localStorage` (if available); it survives navigation, reloads and Finish. Switching language never changes answers, progress or results: both languages share question ids, answer ids, branching and rules, and only the wording comes from different files.

All user-facing text has a Yoruba draft, written with an AI assistant and **not yet reviewed**. While Yorùbá is selected the header says so ("Ìtumọ̀ àkọ́kọ́ ni èyí…"), and draft badges stay on clinical text. Any key missing from a Yoruba file falls back to English and the header says some text is in English. The page's `lang` follows the selected language. The staff-only demo panel stays in English. The doctor-summary PDF is always in English (the built-in PDF font cannot show Yoruba tone marks), and the summary screen says so.

**Correcting Yoruba wording:** edit the text in quotes in

| What | File |
| --- | --- |
| Buttons, start screen, finder, dialogs, audio messages | `content/yo/ui.ts` |
| Questions, answers, helper text, results, summary, consent, privacy, reminders | `content/yo/triage.ts` |
| Disclaimer | `content/yo/clinical.ts` |
| Education cards | `content/yo/education.ts` |

Keep the key names and `${...}` placeholders, then run `npm test` (checks every key exists, no blank text, placeholders kept, and that every character is in the app font). After review, set the file's `...Review.status` to `"approved"` with `reviewedBy` and `reviewedOn`. [docs/yoruba-review.md](docs/yoruba-review.md) lists the terms to check first.

**Font:** `app/fonts/PlusJakartaSans-latin-yoruba-var.woff2` is a subset of Plus Jakarta Sans (OFL) with Latin, ẹ ọ ṣ ń, the combining tone marks and mark positioning. The font has no precomposed ǹ or ḿ, so `lib/i18n/yoruba.ts` writes them as letter plus mark.

## Audio (Listen)

Listen is one shared speaker button (`components/audio/listen-button.tsx`) on every screen: the start screen, the welcome/consent screens, every question (prompt, helper text and answers), "come back later", "result ready", the next steps, the summary, the healthcare finder, the privacy page and the education cards. What the larger screens read, in on-screen order, is in `lib/audio/page-speech.ts`. It reads the selected language only. Each control lists **content ids** (`lib/audio/speech-catalog.ts`), for example `triage.questions.R1.prompt` or `triage.results.outcomes.red.body`; the ids are the same in both languages. For each text, the controller (`lib/audio/audio-controller.ts`) uses, in order:

1. **A reviewed recording** for the current wording: `public/audio/<lang>/<content id>.mp3`, registered in `content/<lang>/audio-map.ts` with the wording's version (a short hash).
2. **Generated speech** from `/api/speech`, if a provider that supports the language is configured. It is labelled "This voice is computer-generated (AI)" while it plays.
3. **A device voice whose language is Yoruba** (or English, for English). An English voice is never used for Yoruba, and setting `lang="yo-NG"` is not treated as a Yoruba voice.

If any text on a control has none of these, the speaker is shown crossed out and pressing it says "Yoruba audio is not available for this screen yet". The button shows a "Listen" tooltip on hover or keyboard focus; pressing it plays, and pressing it again (or during loading) stops. It shows loading, playing and error states (connection, busy, failed). Playback never overlaps, and stops when the question, screen or language changes and when the session ends; pending requests are cancelled.

**Reading along:** nothing plays until the person presses Listen. Once they press it on the start screen or a step of the check, each new step (welcome, questions, "result ready" and next steps) starts reading by itself, and the speaker stays highlighted. It turns off when they stop the audio, change language, open a screen outside the check (finder, summary, learn, privacy) or the session ends.

**Recordings:** `npm run audio:status -- yo` writes `audio-scripts/yo.csv` (content id, file name, version, wording) for the voice artist. Save each file as `public/audio/yo/<content id>.mp3`, then run `npm run audio:status -- yo --register` to record the current versions in `content/yo/audio-map.ts`. When wording changes, its version changes: the old recording stops playing and the status command lists it as outdated. Recordings are played from the server; add them to `PRECACHE_URLS` in `public/sw.js` if they must work offline.

**Generated speech:** `app/api/speech/route.ts` with the adapter in `lib/speech/provider.ts`. The only provider wired in is [Spitch](https://docs.spitch.app/features/speech), whose documentation lists Yoruba (`language: "yo"`; voices Sade, Funmi, Segun, Femi). Set `SPEECH_PROVIDER=spitch`, `SPITCH_API_KEY` and optionally `SPITCH_VOICE_YO` (server-only; see `.env.example`). The browser sends only a content id and version; the server looks up the text itself, so the endpoint cannot speak arbitrary text and never receives answers or summaries. Ids travel in the POST body so access logs do not show which result was read, and nothing is logged. Requests are checked (same origin, JSON, size, known id, current version) and limited per client and per day. Each clip is generated once and cached by provider, voice, language, content id and wording version (memory plus `.speech-cache/`); edited wording gets a new key automatically, and deleting `.speech-cache/` regenerates everything. `npm run audio:warm -- yo <base url>` pre-generates all clips. No Spitch output has been listened to in this project yet, so pronunciation quality is unverified.

## Facility data

**Source in use: GRID3 NGA – Health Facilities v2.0** (CIESIN, Columbia University; released 13 November 2024; [HDX dataset](https://data.humdata.org/dataset/grid3-nga-health-facilities-v2-0), DOI [10.7916/kv1n-0743](https://doi.org/10.7916/kv1n-0743)). Licence: **CC BY 4.0**, confirmed in the HDX metadata (`license_id: cc-by`) and in the dataset's release notes. Required attribution is shown on the finder screen.

- **Coverage:** Lagos State only, 2,798 records (all with coordinates). The publisher describes the dataset as **non-exhaustive and non-validated**; it may omit facilities or include closed ones.
- **Fields used:** name, facility type and level, ownership, state, LGA, ward, coordinates, HFR facility code, upstream origin of the name and coordinates, the source's last-update date and its name-disagreement flags.
- **Not in the data:** street addresses, phone numbers, opening hours and services. The app shows "Street address not available" and never shows phone numbers, hours or services unless a value has been verified.
- **Verification:** no record is verified by EarlyHer. Listing never implies accreditation, current services or specialist breast care.
- **Rebuild:** download `nga_health_facilities_v2_0.gpkg` from HDX, then `node scripts/import-grid3-lagos.mjs <path> --retrieved YYYY-MM-DD`.

**Internal structure** (`lib/types/facility.ts`): one `FacilityRecord` for every source, with per-field provenance (`source`, upstream `origin`, and `verifiedOn`/`verifiedBy` only when actually verified), HFR code, source references with source update date and retrieval date (kept separate), record-level verification status, and flags such as `uncertain-match`. Unknown fields are `null`.

**Other sources (not connected):**

| Source | Status |
| --- | --- |
| Nigeria Health Facility Registry (HFR) | Developer page confirms `https://backend.hfr.fmohconnect.gov.ng/api/v1`, read-only `GET /facilities`, an `X-API-Key` header and a key request form. Filters, pagination, field names, rate limits and reuse terms are **not** published. `lib/facilities/sources/hfr.ts` holds a server-only adapter reading `HFR_API_KEY`; its record mapping deliberately returns nothing until the fields are confirmed. Join to GRID3 by HFR code only. |
| OpenStreetMap / healthsites.io | Not used. ODbL share-alike terms affect combining it with other data; community phone numbers and hours would need verification before display. |
| Curated breast-health services | None. The 2021 canceraware.org.ng list is historical research only; it needs reuse permission and current checks before anything is imported. Nothing is labelled "EarlyHer verified". |
| HEFAMAA, Lagos SPHCB | No public feed found; possible future data-sharing partners. |

**Map and directions.** The map uses Leaflet with tiles from `NEXT_PUBLIC_MAP_TILE_URL`, defaulting to the OpenStreetMap Foundation tile server with "© OpenStreetMap contributors" attribution. That server allows light use only, offers no service guarantee and forbids offline or bulk caching, so **a contracted tile provider (or self-hosted tiles) is recommended for production kiosks**. Tiles are never cached by the service worker. Directions and "Open in Google Maps" use public Google Maps URLs built from the dataset's coordinates. No geocoder is used: search runs over the facility data itself (name, ward, LGA), so it works offline and sends nothing to third parties.

**Location.** "Use my location" asks for permission only when pressed. The position is kept in the screen's memory, used to sort by and show straight-line distance ("in a straight line", never travel distance), and is never stored or sent.

## Telemedicine

Set `NEXT_PUBLIC_TELEMEDICINE_URL` (https) and `NEXT_PUBLIC_TELEMEDICINE_NAME` to an approved provider. Until both are set, the "Talk to a doctor online" option says online consultations are not available through EarlyHer yet.

## Mock and live adapters

`lib/services/index.ts` picks the backend adapters (AI explanation, SMS). `NEXT_PUBLIC_API_MODE=mock` (default) makes no backend calls and labels results as simulated; `http` with `NEXT_PUBLIC_API_BASE_URL` calls the Python backend. The AI explanation and SMS/print dialogs are not shown in the current flows; their adapters and the proposed contracts (`lib/types/api.ts`) are kept for later integration. The N-ATLaS summary API is not integrated.

In `npm run dev` a **Demo states** panel switches the mocks and the facility loader (snapshot, empty, unavailable, offline, error). It is not rendered in production builds unless `NEXT_PUBLIC_SHOW_DEV_FIXTURES=true`.

See `.env.example` for every setting. Server-only secrets (`HFR_API_KEY`) must never use a `NEXT_PUBLIC_` prefix.

## Offline setup and limitations

`public/sw.js` (production builds only) precaches the core screens, their build files, the logo, the manifest and the Lagos facility snapshot. Pages are network-first with a cached fallback; `public/` files are served from cache and refreshed in the background. It never handles non-GET requests, other origins (backend, map tiles, Google Maps) or `/api/`. Each build registers `/sw.js?v=<build id>` so deployments start with fresh caches.

Offline, the start screen, questionnaire, results, and the facility list and search keep working. The map, directions and telemedicine links need a connection, and the screens say so. The first visit needs a connection; service workers need `https://` or `http://localhost`.

## Session privacy

- Answers, results, the SMS phone number and the shared location exist only in page memory. They are never put in cookies or URLs, never sent to a server, and never logged. The healthcare finder reads the result from memory to show the guidance; nothing is passed in the URL.
- **Save my progress on this device** is off by default. Turned on (with a shared-device warning), the triage state is kept in `localStorage` for at most 7 days; "Continue where you left off" and "Start again" are offered on return. Turning it off, **Finish** and the **inactivity timeout** delete it. Set `NEXT_PUBLIC_DEVICE_SAVE=off` to hide it on shared kiosks.
- Consent to use answers for guidance is recorded with its time and policy version (`CONSENT_POLICY_VERSION`). Saving and sharing are separate, explicit choices.
- **Finish** and the **inactivity timeout** (default 120 s plus a 30 s warning) clear the session, abort pending work, remount every screen and return to the start screen.
- Otherwise the only stored value is the language preference.

## Hardware dependencies

- **Printing** uses the browser's print window and never claims a page was printed. `NEXT_PUBLIC_PRINT_LAYOUT=thermal-80` targets 80 mm receipt printers.
- **Audio** (Listen): recordings, then generated speech (needs a connection), then a device voice in the selected language. Most devices have no Yoruba voice.
- **Location** for "Use my location" needs permission and HTTPS (or localhost); kiosks without GPS may report it unavailable.
- **Touchscreen**: the 17-inch kiosk's resolution is not yet known; layouts were checked at 360–1920 px wide. Browser zoom is not disabled.
